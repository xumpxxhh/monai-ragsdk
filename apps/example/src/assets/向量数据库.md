
# PostgreSQL + pgvector：RAG 向量检索

## 1. PostgreSQL + pgvector 是什么

在 RAG（Retrieval-Augmented Generation）系统中，需要将文档转换成向量，然后根据用户 Query 的语义，从大量文档中快速找到相关内容。

PostgreSQL 本身是一个关系型数据库，而 pgvector 是 PostgreSQL 的向量扩展。

因此可以简单理解为：

PostgreSQL
├── 关系型数据
├── JSON / JSONB
├── 全文搜索
└── pgvector
    ├── Vector 数据类型
    ├── 向量相似度计算
    ├── HNSW
    └── IVFFlat

pgvector 的核心价值是：

> 在原有 PostgreSQL 的基础上增加向量存储和向量检索能力。

它不是一个独立的数据库，而是 PostgreSQL 的 Extension。


## 2. 为什么 RAG 需要向量检索

传统数据库比较擅长精确匹配。

例如：

```sql
SELECT *
FROM documents
WHERE department = '技术部';
```
这种查询是根据明确的字段进行过滤。

但是用户可能会问：

> Redis 为什么查询速度这么快？

知识库里可能并没有完全相同的关键词。

例如文档中写的是：

> Redis 基于内存进行数据操作，并采用高效的数据结构和事件驱动模型，因此具有较高的读写性能。

虽然用户的问题和文档的文字并不完全一致，但它们的语义是相关的。

这时候就可以使用 Embedding。

## 3. Embedding 是什么

Embedding Model 可以把文本转换成一个固定维度的向量。

例如：

```
Redis 为什么查询速度这么快？
        ↓
Embedding Model
        ↓
[0.12, -0.35, 0.72, 0.18, ...]
```

文档也会被转换：

```
Redis 基于内存进行数据操作，并采用高效的数据结构……
        ↓
Embedding Model
        ↓
[0.15, -0.31, 0.69, 0.20, ...]
```

如果两个文本语义比较接近，它们在向量空间中的距离通常也会比较近。

因此可以通过计算向量之间的距离来寻找语义相关的文档。

## 4. RAG 中 PostgreSQL + pgvector 的位置

一个典型的 RAG 流程可以分成两个阶段。

### 4.1 离线入库

```
原始文档
   ↓
文档解析
   ↓
Chunking
   ↓
Embedding
   ↓
PostgreSQL + pgvector
```

例如：

```
PDF
 ↓
切成多个 Chunk
 ↓
Chunk 1 → Embedding → Vector 1
Chunk 2 → Embedding → Vector 2
Chunk 3 → Embedding → Vector 3
 ↓
保存到 PostgreSQL
```

### 4.2 在线检索

用户提出问题：

```
Redis 为什么查询速度快？
```

然后：

```
User Query
    ↓
Query Pre-processing
    ↓
Query Embedding
    ↓
Vector Search
    ↓
Top-K
    ↓
Reranker
    ↓
Context
    ↓
LLM
    ↓
Answer
```

所以 pgvector 主要位于：

```
Query Embedding
      ↓
Vector Retrieval
      ↓
PostgreSQL + pgvector
```

## 5. PostgreSQL 中的数据结构

一个简单的 RAG 文档表可以设计成：

```
CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    metadata JSONB,
    embedding VECTOR(1536)
);
```

其中：

```
id
↓
Chunk 的唯一 ID

content
↓
Chunk 的文本内容

metadata
↓
文档来源、页码、标题、部门、时间等信息

embedding
↓
Chunk 对应的向量
```

## 6. 为什么需要 metadata

实际 RAG 中，不能只保存：

```
content
embedding
```

还应该保存大量 metadata。

例如：

```
{
  "document": "redis_manual.pdf",
  "page": 38,
  "section": "高可用",
  "department": "技术部",
  "year": 2025
}
```

这样就可以实现：

```
Vector Search
        +
Metadata Filter
```

例如用户问：

> 查一下 2025 年技术部关于 Redis 高可用的方案。

可以提取：

```
Query:
Redis 高可用方案

Filter:
year = 2025
department = 技术部
```

然后进行：

```
Metadata Filter
        ↓
Vector Search
        ↓
Top-K
```

这通常比单纯依赖向量相似度更加准确。

## 7. pgvector 的 Vector 类型

例如：

```
embedding VECTOR(1536)
```

表示：

> embedding 是一个 1536 维的向量。

例如：

```
[0.12, -0.35, 0.72, 0.18, ...]
```

一共有 1536 个数字。

这里有一个非常重要的要求：

> Vector 的维度必须和 Embedding Model 输出的维度一致。

例如模型输出：

```
1536 dimensions
```

那么数据库就应该定义：

```
VECTOR(1536)
```

不能直接存到：

```
VECTOR(768)
```

## 8. Vector Similarity Search

有了向量以后，就需要判断两个向量之间有多接近。

常见的距离包括：

```
L2 / Euclidean Distance
Cosine Distance
Inner Product
L1 Distance
```

pgvector 提供了对应的操作符：

```
<->    L2 / Euclidean Distance

<=>    Cosine Distance

<#>    Negative Inner Product

<+>    L1 Distance
```

RAG 中最常见的是 Cosine Distance。

## 9. Cosine Similarity

Cosine Similarity 的核心思想是：

> 比较两个向量方向是否相似。

例如：

```
Vector A
   ↗

        ↗ Vector B
```

两个向量方向比较接近，那么它们的语义通常也比较接近。

可以简单理解成：

```
方向越接近
    ↓
Cosine Similarity 越高
    ↓
语义越相关
```

pgvector 使用的是 Cosine Distance：

```
Cosine Distance = 1 - Cosine Similarity
```

所以：

```
Distance 越小
    ↓
Similarity 越高
    ↓
越相关
```

## 10. 最简单的向量检索

假设 Query 已经转换成：

```
[0.12, -0.35, 0.72, ...]
```

可以直接查询：

```
SELECT
    id,
    content,
    embedding <=> '[0.12, -0.35, 0.72, ...]' AS distance
FROM documents
ORDER BY embedding <=> '[0.12, -0.35, 0.72, ...]'
LIMIT 5;
```

这里：

```
embedding <=> query_vector
```

表示计算：

```
Document Vector
        ↓
Cosine Distance
        ↓
Query Vector
```

然后：

```
ORDER BY distance
```

从小到大排序。

最后：

```
LIMIT 5
```

取最相关的 5 个 Chunk。

## 11. Exact Search

如果没有 ANN 索引，可以简单理解为：

```
Query Vector
      ↓
与所有 Vector 计算距离
      ↓
排序
      ↓
Top-K
```

例如数据库中有：

```
Vector 1
Vector 2
Vector 3
...
Vector 1,000,000
```

那么 Query 需要和大量 Vector 进行比较。

优点：

```
结果准确
```

缺点：

```
数据量越大
    ↓
计算量越大
    ↓
查询延迟越高
```

因此在大规模向量检索中，需要 ANN。

## 12. ANN

ANN 全称：

```
Approximate Nearest Neighbor
```

中文：

```
近似最近邻搜索
```

核心思想：

> 不再精确地扫描所有 Vector，而是通过索引快速缩小搜索范围，只搜索最可能相关的候选。

因此：

```
Exact Search

Query
 ↓
全部 Vector
 ↓
Top-K
```

变成：

```
ANN

Query
 ↓
Index
 ↓
候选 Vector
 ↓
Top-K
```

这样可以显著降低查询成本。

pgvector 中最重要的两种 ANN 索引：

```
HNSW
IVFFlat
```

## 13. HNSW 和 IVFFlat 的核心区别

这是后面理解向量数据库最重要的知识点之一。

可以先记住：

```
IVFFlat
→ 分桶

HNSW
→ 建图
```

IVFFlat 的思路：

```
所有 Vector
      ↓
聚类
      ↓
Cluster 1
Cluster 2
Cluster 3
...
      ↓
Query 找相关 Cluster
      ↓
只搜索部分 Cluster
```

HNSW 的思路：

```
所有 Vector
      ↓
建立近邻图
      ↓
Query 从入口节点开始
      ↓
沿着更接近 Query 的节点搜索
      ↓
逐渐接近目标区域
      ↓
Top-K
```

## 14. Exact Search、IVFFlat、HNSW 的关系

可以建立这样的整体认识：

```
Vector Search
│
├── Exact Search
│   └── 扫描所有 Vector
│
└── ANN
    │
    ├── IVFFlat
    │   └── 分桶 / Cluster
    │
    └── HNSW
        └── Graph / 图搜索
```

所以 HNSW 和 IVFFlat 并不是 Embedding Model。

它们也不是 Reranker。

它们属于：

```
Vector Retrieval Index
```

主要负责：

> 如何快速找到与 Query 最接近的向量。

# 15. IVFFlat

## 15.1 IVFFlat 是什么

IVFFlat 是 pgvector 支持的一种 ANN（Approximate Nearest Neighbor）索引。

它的核心思想非常简单：

> 不要搜索所有 Vector，而是先把 Vector 划分成多个 Cluster，查询时只搜索与 Query 最相关的几个 Cluster。

可以把它理解成“先分桶，再搜索”。

整体流程：

```text
所有 Vector
    ↓
聚类（Clustering）
    ↓
多个 Cluster
    ↓
Query
    ↓
找到距离最近的 Cluster
    ↓
搜索部分 Cluster
    ↓
Top-K
```
---
## 15.2 为什么需要 Cluster

假设数据库里有 100 万个 Vector。

如果直接搜索：

```
Query
 ↓
Vector 1
Vector 2
Vector 3
...
Vector 1,000,000
```

需要和大量 Vector 计算距离。

IVFFlat 会先把 Vector 分成很多组。

例如：

```
100 万 Vector
      ↓
   Cluster
      ↓
┌─────┬─────┬─────┬─────┐
│ C1  │ C2  │ C3  │ C4  │
└─────┴─────┴─────┴─────┘
      ...
```

每个 Cluster 中只保存一部分 Vector。

因此查询的时候不需要搜索全部 Vector。

## 15.3 Centroid

每个 Cluster 都有一个中心点，叫：

```
Centroid
```

例如：

```
Cluster 1
    ↓
Centroid 1

Cluster 2
    ↓
Centroid 2

Cluster 3
    ↓
Centroid 3
```

Cluster 中的 Vector 通常距离自己的 Centroid 比较近。

因此可以把整个向量空间理解为：

```
Vector Space

        Cluster 1
       ● ● ●
      ●  C1 ●

                  Cluster 2
                 ● ● ●
                ● C2 ●

       Cluster 3
       ● ●
        C3
```

这里：

```
C1
C2
C3
```

就是不同 Cluster 的中心。

## 15.4 IVFFlat 如何建立索引

可以粗略理解为：

```
原始 Vector
     ↓
K-Means / Clustering
     ↓
得到多个 Centroid
     ↓
每个 Vector 分配到最近的 Centroid
     ↓
形成多个 Inverted List
```

例如：

```
Vector A → Cluster 1
Vector B → Cluster 3
Vector C → Cluster 1
Vector D → Cluster 2
Vector E → Cluster 3
```

最终：

```
Cluster 1
├── A
└── C

Cluster 2
└── D

Cluster 3
├── B
└── E
```

这就是 IVFFlat 的基本结构。

## 15.5 `lists`

IVFFlat 最重要的参数之一是：

```
lists
```

可以理解成：

> Cluster 的数量。

例如：

```
CREATE INDEX documents_embedding_ivfflat_idx
ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

可以理解为把 Vector 划分成大约：

```
100 个 Cluster
```

因此：

```
lists ↑
    ↓
Cluster 数量 ↑
    ↓
每个 Cluster 中的 Vector ↓
```

例如：

```
lists = 10

100 万 Vector
    ↓
10 Cluster
    ↓
平均每个 Cluster 约 10 万 Vector
```

如果：

```
lists = 1000
```

则：

```
100 万 Vector
    ↓
1000 Cluster
    ↓
平均每个 Cluster 约 1000 Vector
```

这里只是帮助理解的平均情况，实际分布不一定完全均匀。

## 15.6 `lists` 太小会怎样

假设：

```
100 万 Vector
lists = 10
```

那么每个 Cluster 可能非常大。

Query 如果只搜索其中一个 Cluster：

```
Query
 ↓
Cluster 3
 ↓
约 10 万 Vector
```

虽然比 100 万少了很多，但候选集合仍然很大。

因此：

```
lists 太小
→ Cluster 太大
→ 搜索候选多
→ 查询可能较慢
```

## 15.7 `lists` 太大又会怎样

如果：

```
lists = 100000
```

那么 Cluster 会非常多。

理论上每个 Cluster 很小，但是 Query 必须更加准确地找到正确的 Cluster。

如果搜索的 Cluster 太少，就可能漏掉真正的近邻。

同时索引本身也会带来额外的管理和构建成本。

所以：

```
lists 不是越大越好
```

需要根据：

```
Vector 数量
Query QPS
Recall 要求
硬件资源
```

进行 Benchmark。

# 16. `probes`

如果说：

```
lists
```

决定：

> 一共有多少个 Cluster。

那么：

```
probes
```

决定：

> 一次 Query 搜索多少个 Cluster。

## 16.1 一个例子

假设：

```
lists = 1000
```

也就是：

```
1000 个 Cluster
```

现在 Query 进来：

```
Query
 ↓
计算与 1000 个 Centroid 的距离
 ↓
找到最接近的几个 Cluster
```

如果：

```
probes = 1
```

就可以理解成：

```
只搜索最相关的 1 个 Cluster
```

如果：

```
probes = 10
```

则：

```
搜索最相关的 10 个 Cluster
```

因此：

```
lists
→ “总共有多少个桶”

probes
→ “这次查询搜多少个桶”
```

## 16.2 probes 对 Recall 的影响

假设真正最相关的 Vector 在：

```
Cluster 8
```

但 Query 判断：

```
Cluster 8
Cluster 12
Cluster 20
...
```

如果：

```
probes = 1
```

可能只搜索：

```
Cluster 12
```

那么：

```
真正相关 Vector
    ↓
没有进入候选集
    ↓
Recall 下降
```

如果：

```
probes = 10
```

Cluster 8 可能进入搜索范围。

因此通常：

```
probes ↑
    ↓
候选 Cluster ↑
    ↓
候选 Vector ↑
    ↓
Recall ↑
    ↓
Latency ↑
```

# 17. IVFFlat 的核心 Trade-off

可以记住：

```
lists
→ 决定索引的空间划分粒度

probes
→ 决定查询时搜索范围
```

查询时：

```
probes 小
    ↓
搜索少
    ↓
速度快
    ↓
Recall 可能下降
```

而：

```
probes 大
    ↓
搜索多
    ↓
Recall 提高
    ↓
Latency 增加
```

# 18. 创建 IVFFlat 索引

使用 Cosine Distance：

```
CREATE INDEX documents_embedding_ivfflat_idx
ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

其中：

```
ivfflat
→ 使用 IVFFlat

vector_cosine_ops
→ 使用 Cosine Distance

lists = 100
→ 创建约 100 个 Cluster
```

## 18.1 设置 probes

例如：

```
SET ivfflat.probes = 10;
```

然后：

```
SELECT
    id,
    content
FROM documents
ORDER BY embedding <=> '[0.12, -0.35, 0.72, ...]'
LIMIT 10;
```

这时候查询会搜索更多 Cluster。

# 19. IVFFlat 的一个重要特点：建立索引前需要有数据

IVFFlat 的 Cluster 是根据已有数据进行聚类建立的。

因此在实际使用中需要特别注意：

```
数据
 ↓
建立 IVFFlat Index
```

而不是完全没有数据就建立一个合理的 IVFFlat 索引。

如果数据量和分布后续发生巨大变化，也需要关注索引效果。

因此：

> IVFFlat 对数据分布和索引构建时机比较敏感。

# 20. HNSW

HNSW 是 pgvector 中另外一种非常重要的 ANN 索引。

全称：

```
Hierarchical Navigable Small World
```

中文一般翻译为：

```
分层可导航小世界图
```

它和 IVFFlat 最大的区别：

```
IVFFlat
→ 分桶

HNSW
→ 建图
```

HNSW 不需要把 Vector 简单地划分成几个 Cluster，而是把 Vector 组织成一个近邻图。

# 21. HNSW 的基本结构

假设有：

```
A
B
C
D
E
F
G
```

如果两个 Vector 比较接近，就建立连接：

```
       A -------- B
      / \          \
     C   D -------- E
      \             /
       F ---------- G
```

其中：

```
节点
→ Vector

边
→ Vector 之间的近邻关系
```

因此 HNSW 本质上是：

```
Vector
  ↓
Graph
  ↓
Nearest Neighbor Search
```

# 22. 为什么 Graph 可以加速搜索

如果使用 Exact Search：

```
Query
 ↓
A
B
C
D
E
F
G
...
```

需要比较大量 Vector。

HNSW 则可以从某个入口节点开始。

例如：

```
            A
          /   \
         B     C
        / \     \
       D   E     F
            \   /
              G
```

Query：

```
Q
```

从：

```
A
```

开始。

如果发现：

```
B 比 A 更接近 Q
```

那么继续：

```
A
 ↓
B
```

然后检查 B 的邻居：

```
D
E
```

如果：

```
E 更接近 Q
```

继续：

```
B
 ↓
E
```

再继续寻找更接近的节点。

最终：

```
Q
 ↓
A
 ↓
B
 ↓
E
 ↓
G
```

不断向更接近 Query 的方向移动。

因此不需要扫描所有 Vector。

# 23. HNSW 的 Hierarchical

HNSW 中非常重要的一个概念是：

```
Hierarchical
```

也就是：

> 分层。

它不是只有一层 Graph，而是多个层。

可以粗略理解：

```
Layer 2

        A -------- G
         \        /
          --------


Layer 1

    A ---- C ---- G
    | \    |    / |
    B  D --E---F  H


Layer 0

A-B-C-D-E-F-G-H-I-J-K-L-M-N...
```

上层：

```
节点少
连接少
搜索范围大
```

下层：

```
节点多
连接多
搜索更加精细
```

因此查询过程大致是：

```
Layer 2
   ↓
快速定位目标区域
   ↓
Layer 1
   ↓
进一步接近目标
   ↓
Layer 0
   ↓
精细搜索
   ↓
Top-K
```

# 24. HNSW 为什么叫“小世界”

Small World 的概念可以简单理解成：

> 图中的任意两个区域，通常都可以通过比较少的跳数到达。

这使得搜索可以通过“跳跃”快速从一个区域到达另一个区域。

不需要：

```
A
→ B
→ C
→ D
→ E
→ F
→ G
→ H
→ ...
```

而是可以通过较短路径快速接近目标区域。

这也是 HNSW 能够高效搜索的核心思想之一。

# 25. HNSW 的 `m`

HNSW 中最重要的参数之一：

```
m
```

可以粗略理解为：

> 一个节点维护多少个邻居连接。

例如：

```
m = 16
```

意味着每个节点会维护一定数量的近邻连接。

可以理解成：

```
m 小
 ↓
图比较稀疏

m 大
 ↓
图比较密集
```

## 25.1 m 太小

如果：

```
m 太小
```

那么：

```
Graph
 ↓
连接少
 ↓
导航路径少
 ↓
可能影响 Recall
```

例如：

```
A —— B —— C

      X
```

某些区域之间可能缺少好的连接。

## 25.2 m 太大

如果：

```
m 太大
```

那么：

```
Graph
 ↓
连接很多
 ↓
索引更大
 ↓
内存消耗增加
 ↓
索引构建成本增加
```

所以：

```
m
```

主要影响：

> HNSW 图本身的结构。

# 26. HNSW 的 `ef_search`

另一个重要参数：

```
ef_search
```

它主要影响：

> 查询阶段到底探索多少候选节点。

例如：

```
ef_search = 20
```

表示搜索时维护一个相对较小的候选范围。

如果：

```
ef_search = 100
```

则会探索更多候选。

一般趋势：

```
ef_search ↑
     ↓
探索更多候选
     ↓
Recall ↑
     ↓
Latency ↑
```

# 27. m 和 ef_search 的区别

这是 HNSW 最容易被混淆的两个参数。

可以这样记：

```
m
↓
建图阶段
↓
图有多密
```

而：

```
ef_search
↓
查询阶段
↓
搜索有多“认真”
```

所以：

```
m
→ Index Construction

ef_search
→ Query Time
```

一个负责：

> “把路修得多密。”

另一个负责：

> “搜索的时候愿意探索多少条路。”

# 28. 创建 HNSW 索引

例如使用 Cosine Distance：

```
CREATE INDEX documents_embedding_hnsw_idx
ON documents
USING hnsw (embedding vector_cosine_ops);
```

然后：

```
SET hnsw.ef_search = 100;
```

执行查询：

```
SELECT
    id,
    content
FROM documents
ORDER BY embedding <=> '[0.12, -0.35, 0.72, ...]'
LIMIT 10;
```

# 29. HNSW 的核心 Trade-off

核心关系：

```
ef_search ↑
    ↓
搜索候选 ↑
    ↓
Recall ↑
    ↓
Latency ↑
```

而：

```
m ↑
    ↓
Graph 更密
    ↓
索引更大
    ↓
内存 ↑
    ↓
构建成本 ↑
    ↓
Recall 通常也会改善
```

因此不能简单地把参数全部调到最大。

真正生产环境应该通过 Benchmark 找到：

```
Recall
Latency
QPS
Memory
Index Build Time
```

之间的平衡。

# 30. HNSW vs IVFFlat

|对比项|HNSW|IVFFlat|
|---|---|---|
|核心思想|建图|分桶|
|数据结构|Graph|Cluster / Inverted List|
|查询方式|图上导航|搜索部分 Cluster|
|主要参数|`m`、`ef_search`|`lists`、`probes`|
|索引构建|通常较慢|通常较简单|
|内存|通常较高|通常较低|
|查询性能|通常很好|很好|
|Recall|通常较高|依赖 `probes`|
|调参|相对直观|需要调 `lists/probes`|
|动态数据|通常比较友好|对数据分布更敏感|

最重要的记忆：

```
IVFFlat
    ↓
分桶
    ↓
lists / probes


HNSW
    ↓
建图
    ↓
m / ef_search
```

# 31. Exact Search vs IVFFlat vs HNSW

把三者放在一起：

```
Vector Search
│
├── Exact Search
│   │
│   ├── 搜索全部 Vector
│   ├── 结果精确
│   └── 大规模数据下速度慢
│
└── ANN
    │
    ├── IVFFlat
    │   │
    │   ├── Cluster
    │   ├── lists
    │   └── probes
    │
    └── HNSW
        │
        ├── Graph
        ├── m
        └── ef_search
```

# 32. 为什么 ANN 会损失 Recall

这是理解 ANN 非常重要的一点。

Exact Search：

```
Query
 ↓
所有 Vector
 ↓
真正的 Top-K
```

理论上可以找到真正的 Top-K。

ANN：

```
Query
 ↓
Index
 ↓
候选 Vector
 ↓
Top-K
```

由于 ANN 会主动缩小搜索范围，因此可能出现：

```
真正最相关的 Vector
        ↓
没有进入候选集
        ↓
被漏掉
```

因此 ANN 是：

```
速度
 ↕
Recall
```

之间的 Trade-off。

一般来说：

```
搜索范围 ↑
    ↓
Recall ↑
    ↓
Latency ↑
```

这也是：

```
IVFFlat → probes
HNSW → ef_search
```

非常重要的原因。

# 34. Embedding、ANN、Reranker 的区别

这三个概念一定不要混淆。

## Embedding

解决：

> 如何把文本转换成能够表达语义的向量？

```
Text
 ↓
Embedding Model
 ↓
Vector
```

## HNSW / IVFFlat

解决：

> 已经有大量 Vector，如何快速找到相似 Vector？

```
Query Vector
 ↓
ANN Index
 ↓
Nearest Neighbors
```

## Reranker

解决：

> 已经召回了一批候选，哪些候选与 Query 真正最相关？

```
Top-50
 ↓
Reranker
 ↓
Top-5
```

因此：

```
Embedding
→ 负责语义表示

ANN Index
→ 负责快速召回

Reranker
→ 负责精排
```

# 36. 什么时候选择 pgvector

如果业务已经大量使用 PostgreSQL：

```
用户数据
业务数据
订单数据
文档数据
Metadata
Embedding
```

那么 pgvector 非常自然。

因为可以：

```
一个 PostgreSQL
    ↓
业务数据
    +
结构化过滤
    +
向量搜索
```

例如：

```
SELECT id, content
FROM documents
WHERE department = '技术部'
  AND year = 2025
ORDER BY embedding <=> '[...]'
LIMIT 10;
```

同时使用：

```
Metadata Filter
+
Vector Search
```

这对于企业 RAG 很实用。

# 37. 什么时候考虑独立向量数据库

如果系统逐渐发展到：

```
超大规模 Vector
+
非常高的 QPS
+
复杂的分布式检索
+
独立扩缩容
+
专门的向量基础设施
```

可以考虑专门的向量数据库，例如：

```
Milvus
Qdrant
Weaviate
Pinecone
```

而 pgvector 更适合：

```
已有 PostgreSQL
+
中小到中大型 RAG
+
希望架构简单
+
结构化数据和 Vector 数据强关联
```

具体选型还是应该根据数据规模、QPS、过滤需求、运维能力和成本进行 Benchmark。
